Demo Arm Forward Kinematics

A seven-joint robot arm that picks something up, carries it across the table, sets it down and waves. Every link is placed by forward kinematics code I wrote in Rust, and a viewer I built draws it live from the /xform_world topic.

One full run of the choreography, recorded from the viewer while make demo was running. The camera drifts around the arm on its own. The readout in the corner shows the state machine's current state.

The robot

The arm is an original design for this project, written as a flat URDF with nine links and eight joints. It stands on a square base, turns on a turret, has a shoulder, an elbow and a flexing wrist, and ends in a rolling hand with two sliding fingers. A fixed joint places a tool tip in front of the hand.

The choreography

The choreography is a table of twelve states. Each state holds a target for the seven movable joints, a tolerance, a short pause, and one transition to the next state. The state machine publishes the target on /joint_trajectory, watches /joint_states, and takes the transition once every joint is within 0.03 of its target.

The fingers close at grasp and open at release. During lift and swing the continuous wrist joint turns past 3 radians, which a limited joint could not do. The last four states are the wave. The joint servo moves each joint toward its target with a first-order response, so the motion eases in and out instead of snapping.

How it is drawn

The viewer is a small web page with no graphics library. A browser cannot open a raw TCP socket, so the hub also serves a local web page and a JSON endpoint that returns the latest /xform_world message. The page asks for it about thirty times a second.

Each message holds one 4x4 matrix per link, stored column by column. For every link the page multiplies that matrix by the link's visual origin and builds the faces of its box, cylinder or sphere in world space. It projects them with a simple perspective camera, sorts the faces from far to near, and fills them with a shade that depends on the face direction. Yellow lines join each joint's parent and child frames, and the small red, green and blue lines are each link's own axes. The scene is z-up, the same as the URDF, and no correction is applied to the robot's frames.

How the kinematics works

All rotation uses unit quaternions. A joint's origin angles are fixed-axis roll, pitch and yaw, and its motion happens after the origin, in the joint's own frame.

R_origin = Rz(yaw) · Ry(pitch) · Rx(roll) T_joint(q) = T_origin · T_motion(q) T_motion = rotate q about the unit axis (revolute, continuous) = translate q · axis, axis as written (prismatic) = identity (fixed) T_root_child = T_root_parent · T_joint T_global_link = T_global_root · T_root_link

The kinematics code never clamps a position to its limits, so it uses the angles and distances exactly as they arrive. A joint that is not named in a /joint_states message returns to zero, and every /tf message carries the timestamp of the joint state that produced it.

How the pieces connect

/param_server/set_paramA client sets robot_description to the URDF text. The server stores it and returns a new version number.
description_statusrobot_state_publisher parses and checks the URDF. A bad description is rejected and the previous robot stays in effect. The status is written only after the new robot is fully loaded.
/joint_statesIn the demo, the joint servo publishes the current angles. Any other client can publish them too.
/tfOne transform per joint, fixed joints included, published at 20 Hz.
/global_poseAn optional pose for the root link. Until one arrives, the root sits at the origin.
/xform_worldrobot_world_state_publisher composes only the latest /tf message with the global pose and publishes every link's 4x4 matrix at 20 Hz.

Everything runs in one Rust program with no external crates. The URDF reader, the XML parser and the JSON parser are my own. Each client gets its own output queue, so a slow client never holds up the others.

Checking it

I wrote sixteen tests in the course's test format. They cover the parameter server, rejection of invalid descriptions, defaults, XML styles, joint-state motion with non-unit axes, the global pose, publishing rate, late subscribers, reloading, and a description close to 1 MiB. I also compared the arm math against a separate matrix implementation on 40 random robots, and every link matched to within 1e-6. The Fetch robot's URDF from the course kit also loads and publishes all of its links.

The arm and its choreography are original to this project, and no third-party robot model appears in the video. I built the software with help from Claude and I reviewed and tested the result.
